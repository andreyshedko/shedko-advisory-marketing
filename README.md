# Shedko Marketing Automation

Рабочее приложение на Next.js 16.4.3 / React / TypeScript с PostgreSQL, Better Auth и серверным SMTP через Nodemailer. Все рабочие цифры читаются из базы. Демо по умолчанию не загружается.

## Локальный запуск

Нужны Node.js 22+ и PostgreSQL 18 (команды `pg_config`, `initdb`, `pg_ctl`, `createdb`).

```sh
npm ci
npm run local:setup
npm run build
npm start
```

Открыть <http://localhost:3000>. Логин и случайный пароль локального администратора сохранены только в `.local/admin-credentials.txt` (права 0600). Не публикуйте этот файл. Локальная база работает через Unix socket; TCP для неё выключен. `.local/`, `.env.local`, `.vercel/` исключены из Git. Секретов в исходниках нет.

Повторный `local:setup` сохраняет данные и учётную запись. Если порт 3000 занят, остановите прежний процесс приложения. Адрес в `BETTER_AUTH_URL` должен совпадать с адресом, который вы открываете. Для изменения порта обновите эту переменную.

Опциональная демонстрационная запись:

```sh
npm run db:seed:demo
```

Она явно отмечена DEMO, исключена из метрик и заблокирована для отправки email.

## Что реализовано

- Десять страниц: обзор, компании/поиск, заявки, переписка, Ads, расходы, задачи, отчёты, подключения, аудит.
- Организации, публичные контакты, источники, ручная проверка, география, тип, причина релевантности, статус и следующее действие. Дубликаты блокируются по регистрируемому домену и нормализованному имени.
- Публичные поисковые ссылки работают без ключа. Подключаемый Brave Search сохраняет результаты как **непроверенные**; проверка источника и добавление компании выполняются оператором. Приложение не обходит авторизацию и не сканирует произвольные внутренние URL.
- Партнёрские программы, источники условий, материалы, персональный черновик, ограниченные переходы статусов. Подача производится самим оператором по ссылке; приложение сохраняет подтверждённый им факт подачи. Платежей и автоматического заполнения внешних форм нет.
- Почтовая цепочка: компания → источник → проверенный контакт → персонализированный черновик → ручное утверждение → отдельное подтверждение SMTP-отправки → событие SMTP и журнал → задача follow-up.
- Изменение текста сбрасывает утверждение. Несохранённые изменения блокируют утверждение и отправку. Версия записи защищает от устаревшего текста во второй вкладке.
- Претензия на отправку записывается в PostgreSQL **до** SMTP. Конкурентный повторный запрос не создаёт ещё одну отправку. Ошибка/тайм-аут даёт `uncertain`; автоматического повтора нет. Зависшая попытка становится `uncertain` при безопасной проверке.
- `sent` означает «SMTP принял», а не доставку или прочтение. После неопределённого результата оператор проверяет корпоративный ящик и вручную фиксирует отправку либо отмену. Приложение не загружает SMTP-письма в папку Sent через IMAP; при необходимости проверяйте журналы провайдера и ящик получателя.
- Один follow-up к исходному письму не раньше семи дней. Задача сама ничего не отправляет. Ответ или отказ блокирует follow-up; отказ подавляет компанию и адрес и отменяет ожидающие письма/задачи.
- Ответы и отказы вносятся вручную с привязкой к письму. **Синхронизация IMAP не реализована** и показана как неподключённая.
- Google Ads: реальный импорт UTF-8 CSV и защищённый приёмник для read-only Google Ads Script. Аккаунты, кампании, показы, клики, CTR, стоимость и конверсии. Повторный импорт обновляет строку по аккаунту/кампании/дню.
- Расходы по категориям, источнику подтверждения и валютам. Валюты не складываются без конвертации. Расходы Ads не нужно повторно вносить вручную.
- Лиды, история переходов в переговоры/предложения/заказы, недельная активность и расходы, скачиваемый Markdown-отчёт. Cron сохраняет отчёт за завершённую неделю. Стоимость привлечения не выдумывается: подтверждённая атрибуция расходов к заказам пока отсутствует.
- Безопасные фоновые проверки: устаревшие подтверждения источников → задача проверки; зависшие попытки SMTP → `uncertain`; дневные бюджетные/аномальные расходы → задача-оповещение; сохранение недельного отчёта. Повторный ежедневный запуск идемпотентен, сбой можно повторить. Все действия без внешних отправок.

## PostgreSQL и авторизация

Схема находится в `migrations/`; миграции версионируются и применяются в транзакции под advisory lock.

```sh
npm run db:migrate
npm run admin:create
```

Для `admin:create` один раз задайте `ADMIN_EMAIL`, `ADMIN_PASSWORD` (14+ символов) и `BETTER_AUTH_SECRET`. Пароль хешируется Better Auth. После создания удалите `ADMIN_PASSWORD` из окружения. Публичная регистрация отключена. Сервер проверяет сессию и точный email администратора на каждом API-запросе. Сессия живёт 12 часов; ограничитель запросов входа хранится в базе. Мутации требуют совпадающий Origin.

Производственная база должна быть отдельной облачной PostgreSQL с пулом соединений и TLS. Локальный socket, `.local/` и локальные пароли для Vercel непригодны.

## Porkbun SMTP

Задайте серверные переменные из `.env.example`:

- `SMTP_HOST=smtp.porkbun.com`
- `SMTP_PORT=587` (STARTTLS обязателен); альтернатива — `50587` с тем же STARTTLS. Для `465` используется TLS с начала соединения. Порт выбирается явно, автоматического переключения нет.
- `SMTP_USER` — полный адрес корпоративного ящика, `SMTP_PASSWORD` — пароль этого ящика.
- `SMTP_FROM` — разрешённый отправитель Shedko Advisory.
- `OUTREACH_FOOTER` — корректная корпоративная подпись и применимые сведения об отправителе.

Подтверждённые оператором параметры Porkbun:

| Протокол | Сервер | Порт | Шифрование |
|---|---|---:|---|
| SMTP | smtp.porkbun.com | 587 | STARTTLS, основной вариант |
| SMTP | smtp.porkbun.com | 50587 | STARTTLS, альтернативный порт |
| SMTP | smtp.porkbun.com | 465 | Implicit TLS |
| IMAP | imap.porkbun.com | 993 | SSL/TLS, справочно |
| POP | pop.porkbun.com | 995 | SSL/TLS, справочно |

IMAP и POP в этой версии приложения не подключены. Настройка имени сервера и порта SMTP без учётных данных не активирует отправку.

Без всех обязательных значений отправка блокируется **до** перехода в состояние попытки. Личный Gmail не используется. Конфигурация не считается проверенным соединением. Аутентификация ящика и результат реальной отправки проверяются при одобренной оператором отправке; серверные секреты и SMTP-ответы с потенциально чувствительным содержимым клиенту не возвращаются.

До первого внешнего обращения оператор проверяет адрес, факты, релевантность, допустимость контакта и корпоративную подпись. Автоматической массовой рассылки нет.

## Google Ads

Формат файла: `public/ads-template.csv`. Один ряд на кампанию и дату:

```csv
account_id,campaign_id,campaign,date,currency,impressions,clicks,cost,conversions
```

Не более 2000 строк и 1 МБ; дата `YYYY-MM-DD`, ISO-валюта, десятичная точка без символа валюты. Экспорт Google с другими заголовками нужно привести к этой схеме. Данные помечаются `csv` / «Импорт CSV». Неверный ряд откатывает всю загрузку.

Для прямого чтения используйте `public/google-ads-script.js`:

1. Установите отдельный случайный `ADS_INGEST_SECRET` длиной минимум 24 символа на сервере.
2. В приватной копии скрипта в Google Ads задайте HTTPS URL `/api/ads/ingest` и тот же секрет. Никогда не коммитьте заполненный скрипт.
3. Подтвердите авторизацию Google Ads Scripts, выполните preview/read-only запуск, затем запуск и расписание. Скрипт читает последние 7 дней, передаёт пакеты по 500 строк и не меняет рекламу.
4. Успешный приём отражается в интеграциях. Настроенный ключ без входящих данных не считается успешной синхронизацией.

Прямая реализация Ads REST API и изменение кампаний не включены. Этот вариант удовлетворяет пути **Scripts и/или API**. В актуальной документации Google от 23.10.2026 указано, что developer tokens отменены 09.09.2026 и доступ API управляется проектом Google Cloud. Поэтому старое требование developer token не зашито в приложение. Для отдельной реализации REST нужны проверка актуальных уровней доступа, OAuth и разрешений аккаунта; не используйте старые резюме страниц вместо их основного текста.

## Бюджеты и Cron

`DAILY_BUDGETS` — JSON порогов по валютам, например `{"USD":50,"EUR":40}`. Это **внутренние пороги оповещений**, а не лимиты рекламного кабинета. `SPEND_ANOMALY_MULTIPLIER` (по умолчанию 2) сравнивает расход текущего UTC-дня со средним за предыдущие 7 дней. Оповещения появляются в разделе задач при проверке; email-уведомления не отправляются. Без порогов остаётся проверка аномалий при наличии истории.

`vercel.json` содержит один ежедневный Cron в 06:00 UTC, `GET /api/cron`. Заголовок `Authorization: Bearer <CRON_SECRET>` обязателен; секрет минимум 24 символа. Vercel добавляет его автоматически при настройке `CRON_SECRET`. Публичный вызов без него возвращает 401. Есть ручной запуск из задач и журнала с проверкой сессии администратора. После неуспеха повтор того же ежедневного ключа разрешён; после успеха — пропускается.

По проверенной документации Vercel на 23.10.2026: Hobby — 100 Cron на проект, каждый не чаще раза в сутки, запуск в пределах часа; Pro — интервалы от минуты. Для этого приложения сохранено одно дневное расписание. **Hobby ограничен личным некоммерческим использованием; для коммерческого применения Shedko Advisory требуется подходящий тариф.**

## Подготовка Vercel

Отдельный проект **shedko-marketing-automation** создан и привязан в пространстве **andreyshedkos-projects**. Существующий сайт `shedko-advisory` не изменялся. Деплой не выполнялся; публичного рабочего URL нет. На момент подготовки у пространства тариф Hobby, production PostgreSQL/SMTP не подключены.

Порядок запуска:

1. Подтвердить подходящий коммерческий тариф и расходы на него. В этой работе тариф не менялся и платные регистрации не выполнялись.
2. Подключить отдельную облачную PostgreSQL, предпочтительно через Vercel Marketplace. Проверить план/условия до создания платного ресурса.
3. Задать `DATABASE_URL`, случайный `BETTER_AUTH_SECRET`, точный HTTPS `BETTER_AUTH_URL`, реальный `ADMIN_EMAIL`, `CRON_SECRET`, а также выбранные интеграции. Не переносить локальный `DATABASE_URL` и тестового администратора.
4. Получить production env в отдельный приватный файл, применить миграции к правильной базе и создать одного production администратора. Не выводить значения секретов и не коммитить env.
5. Выполнить проверки ниже и отдельно подтвердить публикацию приложения. Команда после подтверждения: `npx vercel@65.2.0 deploy --prod --scope andreyshedkos-projects`.
6. Проверить HTTPS, вход и запрет регистрации, публичные 401 для Cron/ingest, работу записей и фактический запуск production Cron. Реальный тест SMTP выполнять только с выбранным получателем и отдельным подтверждением отправки.

Защита Vercel Deployment Protection может работать дополнительно к авторизации приложения. Не включайте защиту, которая блокирует входящий Google Ads Script без специально настроенного исключения; при этом `/api/ads/ingest` всегда должен требовать собственный bearer secret.

## Проверки

```sh
npm run lint
npm run typecheck
npm test
npm run build
# После npm start в отдельном терминале:
npm run test:e2e
```

Unit/integration: отдельная локальная база `shedko_marketing_test`, настоящий PostgreSQL, loopback SMTP без внешних получателей. Тестовая роль должна иметь право создавать эту отдельную базу. Не указывайте production URL в тестовом окружении. HTTP E2E принимает только localhost, создаёт временные записи и удаляет их после проверки; используйте пустую локальную базу, не рабочие данные. Браузерная QA выполнена отдельно; повторный автоматизированный браузерный runner не включён.

Подробный результат — `docs/VERIFICATION.md`. Ограничения: облачный запуск, реальный Porkbun, живой Ads-аккаунт и Brave API без соответствующих секретов не проверены. IMAP отсутствует; прямое управление рекламой и атрибуция CAC отсутствуют. Ввод заявок и регистрации во внешних сервисах выполняются оператором.
